# A3.3 — Seuil de rentabilité : quand le découpage gagne

> **Statut** : mesurée · **Priorité** : P2 · **Programme** : A · **Dépend de** : A3.2 (dure)
> **Ligne de roadmap** : A3.3 · **Fiche de résultat** : archive
> [`roadmap-detail-2026-10-29.md`](../../archive/roadmap-detail-2026-10-29.md) · rapport
> [`prefill-reparti`](../../../reports/rapport-prefill-reparti.md).
> **Résumé** : le découpage gagne quand la latence est faible ; le débit ne compte pas.

## Le besoin

Répartir un modèle sur deux machines n'est pas gratuit : le lien ajoute une attente. Sans
seuil chiffré, « distribuer » est une intuition — et l'intuition se trompe quand la latence
monte.

## L'état

**Mesurée** — l'attente vaut `calcul distant + 3,2 × latence` : **1,01×** à 0 ms, **1,99×** à
5 ms, **4,89×** à 20 ms. Le **débit ne compte pas** (0,25 Mbit/s) : c'est la latence qui coûte.
La porte [`porte-topologie`](../../../tools/porte-topologie.sh) vérifie qu'une couche exécutée
ailleurs rend la même sortie.

## Le contrat

| élément | contenu |
|---|---|
| **entrée** | la topologie (coupe, nœuds), la latence du lien, le calcul distant |
| **sortie** | le facteur d'attente (1,01×, 1,99×, 4,89×) et le verdict de rentabilité |
| **coût** | l'attente, pas le débit |
| **trace** | le flux et la topologie sont rejoués par la porte |

## Contrôles négatifs

- latence nulle (0 ms) : le découpage doit rester ≈ 1× — c'est le plancher ;
- latence élevée (20 ms) : il doit perdre — c'est la pente ;
- le débit augmenté ne doit **pas** changer le verdict.

## Ce qui pourrait le rendre faux

- 3,2 × latence est un coefficient mesuré sur **ce** lien (loopback) ;
- la mesure ne dit rien du **WAN** (hors plan) ;
- le calcul distant est supposé constant : une machine chargée change le seuil.
