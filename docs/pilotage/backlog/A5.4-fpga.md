# A5.4 — Opérateur FPGA complet

> **Statut** : bloquée · **Priorité** : P3 · **Programme** : A · **Dépend de** : A5 · **Bloqué par** : l'accès au rig (4 cartes + ring 40G + Ethernet dédiés, à bringup) et le programme RTL
> **Ligne de roadmap** : A5.4 · **Fiche de résultat attendue** : rapport-a54-fpga.md (à créer dans `reports/`)
> **Résumé** : Exécuter un opérateur complet sur FPGA, alimenté par le même format de flux.
> **Glossaire** : [FPGA](../../theorie/glossaire/entrees/fpga.md) · [PE](../../theorie/glossaire/entrees/pe.md) · [événement](../../theorie/glossaire/entrees/evenement.md).

## Le besoin

Le PE événementiel et le lecteur DDR3 existent et sont vérifiés ; il manque l'accès au matériel
Stratix V **et** les quatre pièces qui font un opérateur complet : contrôleur DDR3 réel, séquenceur
sur les 168 matrices, chemin retour accumulateur → liste, opérations non matricielles en RTL.

## L'état (17/11)

**Le matériel n'est plus le blocage principal** : Stéphane dispose de **4 cartes Stratix V** montées
dans un *mining rig*, reliées **en boucle QSFP+ 40 Gbps** (2 ports par carte), accédées par un
**câble Ethernet dédié**. Ce que la machine de développement n'a pas.

| | 4 cartes | comparaison sur cette machine |
|---|---|---|
| mémoire | **16 Go** (4 × 4 Go DDR3) | = 1 GPU ; 32 Go de VRAM en tout |
| bande passante agrégée | **38,6 Go/s** (4 × 9,66) | RAM 28,7 · GPU 380 |
| débit d'événements | **19,3 G év/s** *projeté* (4 × 4,83) | CPU 5,3 mesuré · 1 GPU 18,1 (dispersion) |
| ring | **4,8 Go/s par lien** | sous la DDR3 d'une carte → **seules les activations traversent** |
| énergie | ~8,3 nJ/év *projeté* → ~160 W | GPU 12,7 nJ → **1,5×**, pas 7× (les 7× sont contre le CPU) |

Les deux conditions que le dépôt s'était fixées sont remplies : « le FPGA n'a de sens qu'à partir de
**2–4 cartes** » ([rapport-cpu-aer](../../../reports/rapport-cpu-aer.md)) et « le ring n'a de sens que
pour des **cartes déportées** » (le doc `multicartes` du dépôt `FPGA-Stratix-V` §3). Mais
la vitesse ne change pas : sur le 0,5 B Q8, 4 cartes plafonnent à ~55 tok/s (DDR3-bound), quand le
CPU mesuré en fait 36,4 et le GPU ~770. **L'intérêt est la démonstration du réparti et l'énergie,
pas le débit.**

**P1 est tranché (17/11)** : la dispersion GPU optimisée atteint **29,37 G év/s** sur **une** carte
(accumulateurs par bancs ; 25,65 G avec atomiques) contre **19,3 G** *projetés* pour **4** cartes.
Le GPU gagne par 1,52× : le **débit ne justifie pas le ring**. Détail :
[rapport-gpu-scatter](../../../reports/rapport-gpu-scatter.md).

## La porte

Un opérateur complet, même résultat que le CPU, mesuré en événements et en temps.

## Contrôles négatifs

- **P1 — fait (17/11)** : la dispersion GPU optimisée fait **29,37 G év/s** > 19,3 G projetés ;
  l'argument de débit du ring est mort, il ne reste que l'énergie, le déterminisme et la démo.
- **P2 — le ring tenu ?** : 4,8 Go/s par lien, mesurés sur deux cartes (DAC 40GBASE-CR4), avant
  d'écrire le protocole.
- **bit-exact** : le même flux CPU/FPGA, version incompatible refusée, opérateur non supporté
  refusé — le modèle d'or est le moteur CPU.

## Prochaine action

**P0** — diagnostic sur le rig (`FPGA-Stratix-V/tools/host_check.sh` : cartes visibles, largeur
PCIe, FTDI/JTAG, I2C des QSFP, OS), puis **P2** (le ring tient-il 4,8 Go/s ?). **P1 est tranché.**
Aucune ligne de RTL avant P2 : le programme est une conquête mesurée, pas un plan de charge.
